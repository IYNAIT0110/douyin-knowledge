## 二、三分钟版：这条视频在讲什么

一句话：**AI 编程的瓶颈已经不在"它会不会写"，而在"你凭什么信"。**

她把这件事画成了一条曲线（现场真的画了图，还玩笑说"别太当科学"）：

| 阶段 | 你的状态 | 能开几个 agent | 卡在哪 |
|---|---|---|---|
| ① 全程盯着 | 每一次工具调用都看，token 逐个读 | 1 个，最多一小把 | 你不信任它，**所以没法并行** |
| ② 能验证 | agent 自己能跑起来、自己看结果 | 几个 | 需要你先把"验证"做出来 |
| ③ 敢放手 | 只在你关心的地方抽查 | 十几个 | 需要代码库有护栏 |
| ④ 自动合并 | 早上醒来 20 个 PR 已在 main 上 | 几十个 | 需要前三个阶段都做完 |

她现在在第四阶段。原话是："我早上醒来，大概 20 个 PR 已经合进去了，而且它们是好的。"她紧接着自己补了一句："这听起来像个 slop artist（批量产垃圾的人），但我保证我不是。"

**她的核心主张不是"多开 agent"，而是反过来的：先让一个 agent 在一个完整问题上变得可信，再谈复制。** pstack 的 README 第一句就是这个意思：*if you want to go fast, go deep first.*

## 三、拆开讲：她到底做对了哪五件事

### 3.1 验证必须闭环，否则你就是人肉传话筒

她自己复盘最惨的一段：刚进 Cursor 第一周，被拉去做 agent 窗口的性能优化，deadline 是一周后发布。她不会这个 codebase，agent 也不会。她的做法是——打开 Chrome DevTools 抓 trace，截图、下载调用树，**发给 agent**，agent 说"看起来是这个东西"，她照着改，结果不是。来回往复，极慢。

她把这个过程命名得很准：**你成了 loop 里的瓶颈（you're just in the loop and a bottleneck），所以没法并行。**

真正的转折点是她写的第一个 skill——**让 agent 自己能跑起来、自己看结果**：

- 能让 agent 启动应用（Electron / Web / iOS 模拟器都行）
- 能取 CPU profile、heap snapshot
- 能通过 Chrome DevTools Protocol 或 Apple 的模拟器工具去**操作界面**
- 于是 agent 改完代码 → 自己跑 → 自己看 → 自己改

一句话总结她的判断：**"这是唯一真正闭环的东西（that's the thing that really closes the loop）"。** 它不保证 agent 写出好代码，但它让 agent **能自己纠错**——而这是"开始信任"的最低门槛。

> 这一条对任何人都成立，不需要在 Cursor 上班：**你的 agent 能不能自己按一下按钮、看到报错、再改一次？** 不能，你就永远是那个复制粘贴报错的人。

### 3.2 能验证还不够，还得"找得到地方"

她把技能做出来之后遇到第二个问题：agent 能跑应用了，**但不知道功能在哪**。

原话很生动：你说"左边栏那个东西"或者"右边 PR 那个 tab"，agent 就**乱撞（flailing around）**，花大量时间找"这个功能到底在哪个 UI 上"，最后只会说"我点这里就行"——却不知道怎么走到那里。

解法是一张 **feature map（功能地图）**：把每个功能的入口、子功能、UI 上的位置、键盘快捷键、以及用 CDP 选择元素用的 DOM 标识，全部写进一个 agent 能读的文件。

为什么这张地图价值远超"文档"：**它把"低质量输入"变成了"可执行的定位"**。她们内部有个 Slack 频道收反馈，很多报告的质量是这样的——一张截图，加一串 `???`（"这是什么？"）。没有地图，agent 只能说"我不知道"；有地图，它能从截图反查到功能，再反查到代码。

配套的是两个 skill：`create`（生成地图，代码里自己扫）和 `maintain`（产品改了，地图跟着更新）。第二个才是长期成本所在。

### 3.3 skill 是从失败里长出来的，eval 是它的单测

她反复强调一句容易被忽略的话：**"维护 skill 其实很难，它需要品味和观察（taste and observation）。"**

她的做法不是"先想一套完美流程"，而是**观察 agent 怎么失败，然后为那个失败写一条 skill**：

- 发现 agent 答"就是这个原因"之前**根本没读那段代码** → 写一条 skill：不许猜，先去读代码
- 发现 agent 把"你这次不该这么写"当成**永久规则**写进注释 → 干脆禁用注释
- 发现 agent 老在 renderer 线程干重活 → 用 CI 禁掉跨进程 import

而 skill 本身也要被测。她的做法是 **eval**，她给的定义很朴素：**"eval 就是给 agent 写的单元测试。"**

| eval 的机制 | 细节 | 为什么这么设计 |
|---|---|---|
| 协调者 + 评分表 | 主 agent 拿一份 rubric，派出多个子 agent | 一次跑多个样本，看分布不看单例 |
| 目录名骗过被评估者 | 子 agent 的工作目录**故意起成看不出在被考的名字** | 她自己说的：agent 能察觉"我在被评估"，然后**改变行为** |
| 跨模型跑 | 在 Cursor 里同一套 skill 跑多个模型，出一张矩阵 | 看这套 skill 是"对某个模型调教出来的"还是"真的稳" |
| 换模型当裁判 | 用**另一个模型**来打分，防止裁判与被测同源而偏袒 | 单一模型自评会系统性偏高 |
| 爬山（hill climb） | `/loop` 循环跑，直到"每项都 10/10" | 把"改 skill"变成可收敛的迭代，而不是手感 |

> `subagent`、`rubric`、`hill climb` 这些词第一次看会晕，第七节有术语表。

### 3.4 角色变了：从厨师变成主厨

她用了两个类比，第二个比第一个好：

**管理类比**：你不信任你的团队 → 你就只能 micromanage（盯着每个人肩膀后面看）→ 你**没法并行**。对 agent 完全一样。

**主厨类比**（她自己更喜欢这个）：你现在是 head chef，**不再炒每一道菜**。你有 line cook、有 sous chef、有分档口。你的工作是**设计厨房**：动线、工位、谁负责什么。

这句话是整个视频的题眼，也是很多人不适应的原因：**能力没有消失，只是从"做"挪到了"设计环境"**。

### 3.5 执行环境：本地看 → 云端跑 → 自动合并

她的建议顺序很硬：**别跳级。**

1. **先在本地**。理由只有一条：**你能看见**。agent 怎么点、怎么调工具、卡在哪，全在眼前。这是唯一能"观察失败"的地方。
2. **再上云**。云端 agent 有自己的电脑、自己的桌面（她们的产品就是这样），能并行几十个。但前提是 3.1 的验证 skill 已经做好，否则你只是把"浪费"放大了几十倍。她原话：还在第一阶段就开几千个云 agent，"你只会烧掉大量 token，而且极其昂贵"。
3. **最后才是自动接活**。她们内部有个 agent 叫 **Benny**：bug 报告进来 → 自己在云端开一台机器 → 用同一套 control skill 复现 → 回报结论。她举的例子是：Benny 复现了那个 bug，同时发现 **main 上已经修好了**，于是她只需要发一个新版本——**省掉她一小时的手工验证**。

**注意第 3 步真正省的不是写代码的时间，是"确认现状"的时间。** 这个观察很值钱：大部分工程时间花在"这是不是已经修了""这是不是我环境的问题"，而不是写那几行代码。

## 四、反面：什么样的代码库配得上这种信任

这是全场最"反潮流"的一段。她明确站到了"别乱重写"的对面一半、又站到了"vibe code 有风险"的这一面。

### 4.1 老代码库（brownfield）其实是被低估的一方

她的判断：**约束做得好的老项目，agent 反而干得不错。** 理由不是老代码写得好，恰恰相反——

> "我经常开玩笑说，AI slop？我们早就有 human slop 了。"

她在 Meta 待过，巨型 monorepo、几万个工程师同时敲键盘。她说不必惊讶：那种体量下代码"其实没那么好"。但**大厂的基础设施本来就是按"团队里最不熟练的那个人"设计的**：框架、约定、护栏、权限收窄（"免得实习生把生产库删了"）。而这些东西**正好是 agent 需要的**。

所以她的结论很实用：**如果你的项目已经有护栏，agent 进来就能干活；护栏是可以后加的，但没有就得先补。**

### 4.2 全新项目（greenfield）才是最大风险

反直觉吧。她的逻辑是：全新项目**一条护栏都没有**。你给 agent 一个任务，它会用**最方便的方式**解决；一次次下来，代码库开始**螺旋失控**——你不理解它，agent "大概理解"，而它优化的是**短期便利**。

她把这个过程说得很直白：**"最后你会在那个应用上吃很多苦。"**

> 这与库里 10-05 王煜全那条的"拼团 vs 聚合"是同一个方向的不同侧面：**规模上来之后，缺的那层结构会以复利方式收账。** 只不过这里收账的对象是代码库。

### 4.3 约束有四层强度，别只靠最软的那层

这是我认为整场最可直接搬走的一张表：

| 层级 | 手段 | 强度 | 她的原话逻辑 |
|---|---|---|---|
| 1 | **架构 / 框架** | 最强 | 框架让"正确写法"成为**最短路径**；agent 天生爱抄现成的，所以它抄到的一定是对的 |
| 2 | **类型系统 / 编译器 / CI** | 强（能让 CI 变红） | "如果代码能编译，那它大概是好的"——她举 Rust 的 borrow checker 为例 |
| 3 | **lint / 静态分析** | 中 | 能拦已知坏模式，但拦不住"没想到的坏模式" |
| 4 | **rules / skills / code review bot** | 弱 | agent 会忘、会不一致；"只靠 rules 和 style guide，你的代码库迟早会变成一团糟" |

她的原则一句话：**"最短的路径就是最好的路径（the shortest path is the best path）"**——因为 agent 一定会走最短路径，那你就把正确解法修成最短的那条。

落到她们的具体做法（这些细节很有说服力，因为都很"小"）：

- 框架叫 **Dune**，可以理解成"给 Electron 应用用的 Next.js"，**设计目标就是让 agent 写**。
- **禁 `useEffect`**——React 里最容易埋坑的钩子，CI 直接报错。
- **禁写注释**——她发现 agent 会把"你这次不该这么写"当成永久规则写进注释，而且写得又臭又长，所以干脆全禁。
- **目录结构强制**：`electron/main`、`electron/renderer` 分开，CI 检查 import 图，**禁止跨层引用**。原因是渲染线程一帧只有 16ms 预算，重活漏进去就掉帧（jank）。
- **功能代码必须同居一个目录**（feature 目录内自带状态、组件、逻辑），agent 80% 的活在一个目录里就能干完。

### 4.4 一条可执行的判据（我认为最该记住的一句）

> **每次你在 PR 里手打"这里不该这么写"，就把这次 review 当成 anti-pattern。**

然后问自己三句：能不能变成 lint 规则？能不能变成 CI 失败？能不能**让这个问题根本不存在**？

她的说法是：**最糟糕的位置，就是"所有约束都靠人肉在 code review 里执行"。** 因为那意味着你的团队规模被你的注意力上限锁死了。

## 五、成本：她的坦白，和一句不该被跳过的话

问答环节有人直接问：这套东西对**没有无限 token** 的普通团队成立吗？

她的回答没有回避，我按原意复述：

- 承认前提：**"我在一个 token 无限的实验室工作，我不能说所有人都该照我这个方式做。"**
- 但她说**可以**在没有这个条件的情况下走到类似位置，关键是把问题换成 **ROI**：前期在 token 上花一大笔（重构、验证、约束），换的是**后面能保持很小很精简的团队**。
- 她给的取舍很具体：**"是招一个人来做这件事，还是花 token 把代码库修到连最笨的 agent 都能干好？"** 她自己答案是后者——因为她的工资很贵，而这个框架"如果放在 pre-agent 时代，靠我一个人要写几年"。
- 一句定性：**"agent 的意义是让你做到你原本做不到的事，不是把 token 撒在每一件小事上。"**

她的成本口径还有一个细节值得记：**她上个月约 1000 个 PR，这个月没过完已接近 800**（媒体转述成"月均两千"，无人审计过那份 PR 列表，她自己说的数字略低）。她主动提了这件事的争议性——**别把数字当结论，把机制当结论。**

## 六、这个人跟你的项目什么关系（我的判断）

你手上是 Electron 悬浮窗 + 飞书 Bitable + 混合语义检索的 Jira 小助手，一个人维护。这条视频几乎每一条都能对上：

| 她的做法 | 你的场景里对应什么 | 现在能不能做 |
|---|---|---|
| 验证 skill：让 agent 自己启动应用看结果 | 悬浮条/展开窗两种形态的启动 + 截图比对 + `kb.json` 检索打分自检 | **能，且是最高优先**。现在每次改 UI 都要你截图反馈，这正是她说的"你在 loop 里当瓶颈" |
| feature map | tabs / 区域下拉 / 检索框 / 反向查询入口的定位表（含 DOM 选择器） | 能，规模小，一小时能写完 |
| eval = agent 的单测 | 混合打分（0.65 语义 + 0.35 关键词）跑一组固定 query，看排序是否退化 | 能，**这是你最该有的回归测试**——改权重时现在只能靠手感 |
| 把 review 变成 lint | 你自己反复纠正的那几条（单行布局、不用两行换行）写成 lint/CI，而不是每次口述 | 能 |
| 约束优先于提示 | 与其在 prompt 里写"别写两行"，不如让组件层面根本排不出两行 | 能，但改动大，看性价比 |

一句话：**你不缺"让 agent 写代码"的经验，你缺的是"让 agent 自己知道写对了没有"的那层设施。** 而这一层恰好不需要在 Cursor 上班也能做。

## 七、术语表 + ASR 订正（初学者向）

她讲得快、口音轻，自动字幕错得不少。以下是**影响理解**的订正（其余人名/产品名已按外部资料核实）：

| 字幕 | 实际 | 说明 |
|---|---|---|
| the best of you of AI | the best **use** of AI | 开场第一句，漏词 |
| vive code | **vibe** code | 凭感觉让 AI 写，不看代码 |
| control glass | control **Glass** | Glass 是 Cursor agent 窗口的内部代号 |
| Pstack / PAC / P | **pstack** | P = **potato**（她的网名 @poteto），故意调侃 Gary Tan 的 GStack |
| GStack | **GStack** | YC 的 CEO **Garry Tan** 的插件；她说"我们同姓，但没关系" |
| Grockbot / graphbot / grabbot | **Grok Bot** | 她们的新产品，8-11 进 beta |
| Grock 4.6 | **Grok 4.6** | 结尾顺带提的模型更新【按语境推定】 |
| Dune | **Dune** | 她们自研的 Electron 框架 |
| bug bots / bogbot | **BugBot** | Cursor 的代码审查 bot |
| /loop | **/loop** | pstack 里的循环指令 |
| slop artist | **slop artist** | 她自嘲"批量产垃圾的人" |

关键术语（按出现顺序）：

- **skill**：一个 markdown 文件（`SKILL.md`），告诉 agent"这类活该怎么干"。不是代码，是流程知识。
- **subagent**：主 agent 派出去干活的子 agent，各自有上下文。
- **eval**：给 agent/skill 写的自动化测试，跑一批任务看是否达标。
- **rubric**：评分表，写明"什么算做到"。
- **hill climb**：反复迭代往高分爬，不追求一次到位。
- **brownfield / greenfield**：老项目 / 全新项目（建筑业借来的词）。
- **CDP**（Chrome DevTools Protocol）：用程序控制浏览器的接口；agent 靠它点按钮、读 DOM。
- **heap snapshot / CPU profile**：内存与性能快照，用来定位卡顿。
- **jank**：掉帧、卡顿；60fps 下每帧只有 16ms。
- **monorepo**：所有代码放一个巨型仓库（Meta 那种）。
