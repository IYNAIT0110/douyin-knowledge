### 3.4 词覆盖：把口径钉死

README 原写「5677 个实词里只有 56 个查不到，99.01%」。今天实测三种算法，**没有一个能复现 5677**：

| 口径 | 分子 / 分母 | 覆盖率 |
| --- | --- | --- |
| 按出现次数 | 17700 次引用，85 次查不到 | **99.52%** |
| 按去重原词（全库合并） | 3165 个原词，56 个查不到（50 类 lemma） | **98.23%** |

`56` 能对上第二行的"查不到的原词数"，但 `5677` 既不是 3165、也不是 17700、也不是 6433 —— **分子分母来自两套算法**，所以那个 99.01% 是伪精确。

## 五、本次的收获（已进 README）

**一、回填是"补文件"，不会自动"补链接"。** 三件套越可能是事后补的，主报告就越可能永远停在"待补"。判据：**每次回填，必须回头改当天主报告那一行** —— 否则"仓库里有文件"和"读者能点到"是两件事。

**二、修 README 不等于修全库。** 10-26 只在 README 改了时窗表述，`notes/2026-09-11.md` 里同一句错照旧躺着。**同类表述要全库 grep 一遍，不能只改读到的那一份。**

**三、路径是字符级问题，必须机器验。** 人眼对 `好用`/`用好`、全角/半角、连字符差异基本无感；一条 `os.path.exists` 就够了。这也是为什么把它固化成脚本而不是"下次注意"。

**四、至今为止，出错最多的不是"提炼得不好"，而是"周边设施没人看"** —— README 说错（10-26）、路径指错（10-28）、改完不提交（10-28）。内容检查做了十一轮，产出质量已经稳定；**剩下的风险几乎全在"文件系统层面"**。下一轮补洞建议继续往这个方向走。
