# Part B · 论证展开（整段对照）
# Part B · The Arguments, Paragraph by Paragraph

## B1. 微观管理的经济学 / The Economics of Micromanagement

**EN** If I'm a manager and I don't trust my team, the only mode I have is micromanagement. I stand over my reports' shoulders all day, checking that they're working, that nothing broken ships. That is not a higher-quality team — it is a slower team with the same headcount. Agents work the same way. If I don't trust the output of one agent, I can't spawn a hundred of them. So the number of agents I can run is not a function of how good the models are. It is a function of how much of the checking I have managed to move off my own eyes.
> **中** 如果我是一个不信任团队的经理，我唯一的工作模式就是微观管理：整天站在下属肩膀后面盯着，确认他们在干活、确认没把坏东西发出去。这不是质量更高的团队，这是**同样的编制、更慢的速度**。agent 完全一样。如果我不信一个 agent 的输出，我就开不了一百个。所以我到底能跑几个 agent，不是模型多强的函数，而是**我成功把多少检查从自己眼睛上挪走**的函数。

## B2. 第一周：我就是那个人肉中继 / My First Week: I Was the Human Relay

**EN** When I joined Cursor five months ago, I was supposed to join a different team, but since I had experience working on React and the window is a React application, I was asked to help with the agent window. There wasn't a lot of skill that could help me. The window was going to launch in a week, so I sat there and opened Chrome DevTools, took tracing, looked at the flame graph myself, and tried to make sense of it — in my first week, with no idea what I was looking at. And my agent had no idea either. I would take a snapshot of the tree, send it to the agent, and it would say, yeah, it kind of looks like this, and confidently point at something. I'd fix that, and it turned out that wasn't the actual thing.
> **中** 五个月前我加入 Cursor，本来是要去另一个团队的，但因为我在 React 上有经验、而这个窗口本身就是 React 应用，就被拉来帮忙做 agent 窗口。当时没什么技能能帮上我。窗口一周后就要发布，所以我就坐在那儿打开 Chrome DevTools、抓 trace、自己看火焰图、努力理解它 —— 那是我入职第一周，我根本看不懂自己在看什么。我的 agent 也不懂。我会把调用树快照下下来发给它，它说"嗯，看起来像是这个"，还很自信地指着某个地方。我照着改，结果根本不是那个东西。

## B3. 为什么"确认现状"最贵 / Why Confirming Reality Is the Expensive Part

**EN** We have an agent called Benny. It takes the bug reports we get, spins up a cloud machine, runs its own desktop, and uses the same control skills to interact with the application and try to reproduce the issue. In the example I showed, Benny reproduced the bug and also found that it was already fixed on main — so all I needed to do was release another build. That is huge information. I didn't have to sit with an agent for an hour figuring out whether this was fixed or not. Notice what got saved there: not the time to write a fix, because there was no fix to write. What got saved was the hour of establishing what is actually true right now.
> **中** 我们有个 agent 叫 Benny：它接手收到的 bug 报告，在云端开一台机器、跑起自己的桌面，用同一套控制技能去操作应用、尝试复现。我演示的那个例子里，Benny 复现了 bug，同时发现 main 上其实已经修好了 —— 那我只需要再发一个版本。这是巨大的信息量。我不用陪着 agent 耗一个小时去搞清楚"这到底修了没有"。注意这里省掉的到底是什么：不是写修复的时间，因为压根没有修复要写；省掉的是**那一个小时用来确认现状**的时间。

## B4. 老项目被低估了 / Brownfield Is Underrated

**EN** A lot of big-company problems are now everyone's problems. I worked at Meta — we had a giant monorepo, tens of thousands of engineers banging on keyboards and shipping. A lot of really great engineers, but I'll say, you'd be surprised how not-that-good the code actually is. I often joke that AI slop — we had human slop. And big tech infra is actually designed for that: you build for the least capable engineer on your team. You build frameworks, you build conventions, you build guardrails, you restrict credentials so your intern doesn't wipe the production database. If you already have that kind of infra, agents can do a very good job, because the guardrails are already in place.
> **中** 很多"大公司才有的问题"现在成了所有人的问题。我在 Meta 待过 —— 巨型 monorepo，几万个工程师一起敲键盘、一起发布。里面有很多非常优秀的工程师，但我得说，你会惊讶于那些代码其实没那么好。我常开玩笑：AI 产的垃圾？我们早就有**人类产的垃圾**了。而大厂的基础设施本来就是为这个设计的：你按"团队里最不熟练的那个人"来设计。你做框架、做约定、做护栏、收窄权限，免得实习生把生产库删了。如果你已经有这套东西，agent 其实能干得很好，因为护栏已经在那儿了。

## B5. 最短的路就是最好的路 / The Shortest Path Is the Best Path

**EN** There are multiple layers of enforcement, and they are not equally strong. Architecture and framework is the strongest, because agents love to copy existing patterns — whatever they copy will be right. Then the type system and CI, which can actually turn red. Then lint and static analysis, which catch the bad patterns you already thought of. Then rules, skills, and review bots, which are soft — the agent can forget, or apply them inconsistently. If you only have rules and a style guide, it's only a matter of time before your codebase looks like complete garbage. One of my key principles for a framework is: the shortest path is the best path — because that plays exactly to how agents love to write code. They take shortcuts. So why not make the best way to solve the problem the shortcut?
> **中** 约束是分层的，而且强度并不相同。架构和框架最强，因为 agent 天生爱抄现成的 —— 它抄到的一定是对的。然后是类型系统和 CI，它们真的能让构建变红。再然后是 lint 和静态分析，只能拦住你已经想到的坏模式。最后是 rules、skills 和审查 bot，这些是软的：agent 会忘，也会用得前后不一致。如果你只有 rules 和一份风格指南，那你的代码库迟早会变成一团垃圾。我对框架的一条核心原则是：**最短的路就是最好的路** —— 因为这正好顺着 agent 写代码的天性。它们就走捷径。那为什么不把"正确解法"修成那条捷径？

## B6. Token 与 ROI / Tokens and ROI

**EN** I work at a lab where we have unlimited tokens, and I definitely cannot claim everyone should do this the exact same way I did. But I think it's possible to get to this point without the bank. If you're a leader, or you have a startup, to me it's a question of ROI. Yes, you spend a lot of money on tokens up front — refactoring a codebase takes a lot of tokens. But if we're heading to a world where agents write all the code, you want to stay very lean. So the trade-off is: do you hire someone to do this, or do you spend the tokens to set up a codebase where even the most naive, dumbest agent can do a good job? For me, agents are all about allowing you to do things that you couldn't do before. It's not just about spending tokens on every single little thing.
> **中** 我在一个 token 无限的实验室工作，我绝对不能声称所有人都该照我这个方式做。但我认为，没有这个家底也能走到这一步。如果你是负责人，或者你在带一家创业公司，对我来说这就是个 **ROI** 问题。是的，你前期要在 token 上花很多钱 —— 重构一个代码库要烧掉大量 token。但如果我们要走向"agent 写所有代码"的世界，你会希望团队非常精简。所以取舍是：**你是招一个人来做这件事，还是花 token 把代码库修到连最笨的 agent 都能干好？** 对我来说，agent 的意义是让你做到你原本做不到的事，而不是把 token 撒在每一件小事上。

## B7. 约束的意外红利 / The Unexpected Dividend of Constraints

**EN** Before Grok Bot, Cursor only had developer tools — the agent window, the CLI, the IDE. You could do your work in them, but they weren't optimized for people who aren't developers. Grok Bot is basically the Cursor moment for people who are not in tech, because it is a very accessible way to use agents in a familiar interface. And the reason our PMs and designers can now ship features directly is not that the model got smarter. It is that Dune's constraints are strict enough that someone who doesn't know the codebase can't wreck it. They fix a bug, say, can you take a look — and I just stamp it. That's the payoff: guardrails don't limit people, they let you hand out capability.
> **中** 在 Grok Bot 之前，Cursor 只有开发者工具 —— agent 窗口、CLI、IDE。你可以在里面干活，但它们不是为非开发者优化的。Grok Bot 基本上就是"非技术人员的 Cursor 时刻"，因为它用熟悉的界面把 agent 变得很容易上手。而我们的 PM 和设计师现在能直接交付功能，原因不是模型变聪明了，而是 **Dune 的约束足够硬，不懂这个代码库的人也搞不坏它**。他们修完一个 bug 说"你看一下"，我直接盖章。这就是回报：护栏不是在限制人，而是让你能把能力发出去。

## C2. Sixteen Milliseconds

**EN** One example we suffer from a lot in the agent window is very poor isolation between processes. On Electron you have a renderer thread that draws your UI, and you also have a thread that can run other code that doesn't need to block the UI. We do a poor job of separating those, so code that gets pulled in often ends up running on the renderer thread — and all of a sudden you're competing with the renderer. If you want 60 frames per second, every frame has to be drawn in 16 milliseconds. That is a very small deadline per frame. Start accidentally bringing in heavy work, or anything with a lot of IO, and you get jank: your FPS drops, you lose frames, and the experience turns choppy. So in Grok Bot we literally have directories called `electron/main` and `electron/renderer`, and an import CI check that walks the import graph to make sure you're not importing code from one into the other.
> **gloss** *renderer thread* = the thread that paints the UI; *jank* = visible stutter; *import graph* = which file imports which.

<details>
<summary>中文自查（别对着读）</summary>

在 agent 窗口上我们长期吃亏的一个例子，是进程之间隔离做得很差。Electron 里有一个画 UI 的渲染线程，也有一个可以跑其他代码、不必阻塞 UI 的线程。我们没把两者分好，所以被引入的代码经常落到渲染线程上跑 —— 于是突然之间你就在跟渲染抢资源。想要 60 帧，每一帧只有 16 毫秒，这个期限非常紧。一旦不小心把重活、或者大量 IO 带进来，就掉帧（jank）：帧率下降、丢帧、体验变得一顿一顿。所以 Grok Bot 里我们真的建了 `electron/main` 和 `electron/renderer` 两个目录，还有一个 import 检查，走一遍 import 图，确保你不会从一个目录引到另一个。

</details>

## C3. The Softest Layer

**EN** Rules, skills, and BugBot are the soft layers. The agent can still forget — it can, or it may not always consistently apply them. So I like to layer them, but I don't like to rely on them as the only source of enforcement, because they are very, very soft. If you only have rules and BugBot and a style guide for your code, it's only a matter of time before your codebase looks like complete garbage. I'm sorry to say that. So I recommend: things that can be enforced, should be enforced. That's also why the choice of tech stack matters — Rust is getting super popular again because the compiler is so strict. As long as you don't let your agents write unsafe blocks, if the code compiles, it's probably good.
> **gloss** *enforcement* = the act of making a rule actually binding; *unsafe block* = Rust's explicitly-marked escape hatch; *a matter of time* = will inevitably happen.

<details>
<summary>中文自查（别对着读）</summary>

rules、skills 和 BugBot 都是软层。agent 还是会忘 —— 它可能忘，也可能用得前后不一致。所以我喜欢把它们叠起来用，但不喜欢把它们当作唯一的约束来源，因为它们实在太软了。如果你只有 rules、BugBot 和一份风格指南，你的代码库迟早会变成一团垃圾。这话不好听。所以我的建议是：**能被强制的，就该被强制**。这也是为什么技术栈的选择很重要 —— Rust 又火起来了，因为编译器足够严格。只要你不让 agent 写 unsafe 块，代码能编译，那它大概就是好的。

</details>

## C4. What the Designers Do Now

**EN** I talk to our PMs a lot. One agent per project, and they can have an agent that summarizes what Lauren did last night — so they know what I did, without asking me. And they're shipping code too. Very often they'll just say, here's a bug, I fixed it, can you take a look — and then I go review it, and actually it's perfect. I just stamp it. The strict constraints of Dune allow people who are not experts in the codebase to contribute at a high level. So designers and PMs are able to ship features directly, and that makes the Grok Bot team super fast.
> **gloss** *stamp it* = approve without further review; *at a high level* = to a high standard, not "high-level overview".

<details>

我经常跟我们的 PM 聊。一个项目一个 agent，他们可以让 agent 总结"Lauren 昨晚做了什么" —— 不用问我，就知道我干了什么。而且他们也在交付代码。经常是他们说：这儿有个 bug，我修了，你看一眼 —— 我去审，结果真的完美，我直接盖章。Dune 那些严格的约束，让不熟悉这个代码库的人也能高标准地贡献。所以设计师和 PM 能直接交付功能，这让 Grok Bot 团队快得离谱。
