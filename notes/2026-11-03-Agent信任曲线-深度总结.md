## 一、先把问题摆正：这不是能力问题，是信任问题

大多数人讨论 AI 编程，问的是"它能不能写对"。Lauren Tan 把问题换掉了。

她的开场第一句就把定位说清楚了：

> "the best use of AI is really as a pair programmer — not a tool to just replace the act of writing code, or worse, outsourcing thinking."

注意这句话里有两个否定。它否定的不是"AI 能不能写代码"，而是两种**关系形态**：

1. 把 AI 当成**替代写代码这个动作**的工具（于是你只关心产出物）；
2. 把 AI 当成**外包思考**的对象（于是你连判断都交出去了）。

她主张的第三种形态是**结对**——你还是那个负责判断的人，AI 是那个打字更快的同伴。这个定位一旦确立，接下来的问题就自然变了：结对编程里最重要的事从来不是"对方打字快不快"，而是**你敢不敢让他直接改你的分支**。

所以她整场只回答一个问题：**怎么建立这份信任。**

这不是修辞。她给了一个很具体的失败案例来证明"信任"是真实的瓶颈，而不是软性话题：

她刚进 Cursor 第一周（2026-03），本来要去做云团队，因为做过 React 被拉去救 agent 窗口的性能问题，一周后就要发布。她不懂这个代码库，agent 也不懂。她的工作流是：打开 Chrome DevTools 抓 trace → 截图 → 下载调用树 → 发给 agent → agent 说"大概是这个" → 她照着改 → 不是。反复。

她对这个过程的总结只有一句，但这句话是整场的枢纽：

> "you're just in the loop and a bottleneck. So there's really no way to parallelize."

**瓶颈不是 agent 不够强，是"你在环里"这件事本身。** 只要每一个判断都必须经过你的眼睛，agent 的数量就只是个装饰。

这里有一个容易滑过去的逻辑跳跃，值得停下来看清：**并行度不是由 agent 能力决定的，是由你的验证带宽决定的。** 你可以同时开一百个 agent，但只要每个结果都要你看一眼，你的吞吐量就等于"你看一眼的速度"。这才是她后面所有工程手段要解决的问题——**把验证从你的眼睛上卸下来，装到 agent 自己身上。**

## 二、第一阶段：让 agent 自己闭环

她做的第一件事不是写更好的 prompt，是写一个 skill（技能文件，本质是一个 `SKILL.md`），让 agent **自己能把应用跑起来、自己看结果**。

清单很短，但每一条都在拆掉一个"必须问你"的环节：

| 能力 | 拆掉了哪个环节 |
|---|---|
| 启动应用（Electron / Web / iOS 模拟器） | 不用你手动起服务、手动点开 |
| 取 CPU profile、heap snapshot | 不用你截图性能面板 |
| 通过 CDP 或 Apple 模拟器工具**操作界面** | 不用你手动点按钮复现 |
| 拿回结构化结果（JSON） | 不用你肉眼读日志再转述 |

她的原话是：**"that's the thing that really closes the loop."**

这句话要读准。"闭环"在这里不是形容词，是一个可以判定的技术状态：

> **agent 改完之后，能不能不经过人，自己获得一个"对/错"的信号？**

能，就是闭环；不能，你写再好的 prompt 也只是让它猜得更像。

**闭环之后发生了什么，比闭环本身更重要。** 她说了两层意思：

- 第一层，它**不保证** agent 写出好代码（"it doesn't guarantee your agent writes good code"）；
- 第二层，它让 agent **能自己纠错**（"it allows them to at least correct code"）。

这两句话合起来是一个很重要的认识：**验证的价值不在于"筛掉坏结果"，而在于"让坏结果在被你看到之前就自己变好"。** 前者只是质检，后者才是产能。

这也是为什么"我每次都仔细 review AI 的代码"听起来很负责、实际上是这套系统里最贵的一环。她自己算过这笔账：

> "when I use AI I save some time writing the code, but I actually find myself spending more time reviewing what the AI did and correcting it."

写代码省下来的时间，被 review 吃回去了，还多付了注意力。这就是"你在环里"的经济学解释。

## 三、第二阶段：让它找得到地方（feature map）

有了闭环之后，第二个瓶颈立刻出现，而且非常朴素：**agent 不知道功能在哪。**

她描述得很具体：你说"左边栏那个东西"、"右边 PR 那个 tab"，agent 就开始**乱撞（flailing around）**，花大量时间找"这个功能到底在 UI 的哪里"，最后只会说"我点这里就行"，却不知道怎么走到那里。她的评价是："体验非常糟糕。"

解法是一张 **feature map（功能地图）**：把每个功能的入口、子功能、UI 位置、键盘快捷键、以及通过 CDP 选择元素用的 DOM 标识，全部整理成 agent 能读的文件。

我认为这张地图的价值被低估了，原因不在"文档更全"，而在于它改变了一类输入的可用性：

**它让"低质量输入"变成"可执行的定位"。**

她们内部有个 Slack 频道收用户反馈，很多报告长这样：一张截图，加一串 `???`。没有地图，agent 的合理反应是"我不知道你在说什么"；有地图，它可以从截图反查到功能、从功能反查到代码。同一份烂输入，一个变成了死路，一个变成了工单。

顺带一个工程细节值得记：她配套做了两个 skill，`create`（扫代码生成地图）和 `maintain`（产品变了就更新）。**第二个才是长期成本。** 地图会腐烂，而腐烂的地图比没有地图更危险——agent 会自信地按错的路径走。

## 四、第三阶段：把每一次失败固化成一条技能

到这里她给了一句我认为全场最诚实的话：

> "maintaining skills is actually hard. It requires a lot of taste and observation."

注意她没有说"要多写 skill"，她说的是**维护**难，难在**品味和观察**。这句话把"skill 工程"和"提示词工程"彻底分开了：前者是持续观察失败模式，后者是一次性写好一段话。

她的方法论是一个循环，不是一份清单：

```text
观察失败  →  定位失败在哪一步  →  为这一步写一条 skill  →  用 eval 验证 skill 真的管用  →  继续观察
```

三个真实例子，每个都能看出"skill 是从失败里长出来的"：

| 观察到的失败 | 写下的 skill |
|---|---|
| agent 断然说"就是这个原因"，但工具调用记录显示**它根本没读那段代码** | "不许猜，先去读代码"（她给这条取名叫 `how`，用来问"这代码是怎么工作的"） |
| agent 把"你这次不该这么写"当成**永久规则**写进注释，而且写得又臭又长 | 干脆**禁止写注释**（CI 层面） |
| agent 老把重活放渲染线程，导致掉帧 | import 图检查，**禁止跨进程引用** |

### eval：给技能写单元测试

她自己给的定义最省事：**"eval 就是给 agent 写的单元测试。"**

机制拆开看，每一步都有明确的设计意图：

| 机制 | 做法 | 为什么 |
|---|---|---|
| 协调者 + 评分表 | 主 agent 拿 rubric 派出多个子 agent | 看分布稳定性，不看单次表现 |
| 目录名伪装 | 子 agent 的工作目录**故意起成看不出在被考的名字** | 她原话：agent 能察觉自己在被评估，**然后就改变行为** |
| 跨模型矩阵 | 同一套 skill 在多个模型上跑，出一张表 | 分辨这是"调教某个模型"还是"真的稳" |
| 换模型当裁判 | 用**另一个模型**打分 | 同源自评会系统性偏高 |
| 爬山 | `/loop` 一直跑到每项 10/10 | 把改 skill 变成可收敛的迭代，不靠手感 |

**"目录名伪装"这一条值得单独说。** 它意味着一个不舒服的事实：**agent 在被观察时会表现得更好**。那么你所有"我盯着它的时候它挺好的"的经验，都不能直接外推。要判断一个 skill 是否真的有效，必须让它在**不知道自己被考**的条件下跑——这跟我们做用户测试时避免主试效应是同一个道理，只是对象换成了模型。

## 五、角色：从厨师变成主厨

她对"工程师变成什么"给了两个类比，第二个更好用。

**管理类比**：你不信任你的团队，你唯一能采取的工作模式就是 micromanagement——盯着每个人肩膀后面看。结果不是质量更高，是**你没法并行**。对 agent 完全一样。

**主厨类比**：你现在是 head chef，**不再炒每一道菜**。你有 line cook、有 sous chef、有分档口。你的工作是**设计厨房**：动线怎么走、每个工位负责什么、食材放哪。

这个类比精确的地方在于：**主厨并没有失去厨艺，他只是不再亲手执行。** 而多数人对 AI 的焦虑恰恰来自"我不亲手写代码了，我的价值在哪"——答案是不在"写"上，在**设计那个让别人（或别的 agent）能稳定写出好东西的环境**上。

她还补了一句更硬的：这套 skill 不只是让你一个人变强，"**it levels up your whole team, even your whole company**"。理由很实在——一旦验证和约束都在代码里，团队里任何人都能安全地接活。

## 六、顺序不能颠倒：本地 → 云端 → 自动接活

她的建议有明确次序，而且明确反对跳级。

**第一步，在本地。** 理由只有一条：**你能看见**。agent 怎么点、怎么调工具、卡在哪一步，全在眼前。这是唯一能"观察失败"的地方，而观察失败是写 skill 的唯一原料。

**第二步，上云。** 云端 agent 有自己的机器、自己的桌面，能并行几十个。但前提是第一阶段做完了。她的话很直接：如果还在"全程盯着"的阶段就开几千个云 agent，**"你只会烧掉大量 token，而且极其昂贵"**。

**第三步，自动接活。** 她们内部有个 agent 叫 **Benny**：bug 报告进来 → 自己在云端开一台机器 → 用同一套 control skill 复现 → 回报结论。

她举的例子值得逐字看，因为它揭示了自动化真正省下的是什么：

> Benny 复现了那个 bug，**同时发现 main 上已经修好了**，所以她只需要发一个新版本。

这里省掉的不是"写修复代码"的时间（本来就没有代码要写），而是**"这到底修了没有"的确认时间**——她原本要花一小时让一个 agent 去查。

**这是一个反直觉但很重要的观察：工程时间里最大的一块不是"做"，是"确认现状"。** 而"确认现状"恰恰是最容易被闭环掉的活。

## 七、反面：不是所有代码库都值得被信任

这是全场最反潮流的一段，也是我认为最该带走的一段。她的立场两边都不讨好：既反对"新项目就 vibe code"，也反对"老项目一律不能重写"。

### 7.1 老项目被低估了

她的判断：**约束做得好的老项目，agent 反而干得不错。**

理由不是老代码写得好，恰恰相反：

> "I often joke that, you know, AI slop — we had human slop."

她在 Meta 待过，巨型 monorepo、几万人同时提交。她说别惊讶，那种体量下代码"其实没那么好"。但**大厂基础设施本来就是按"团队里最不熟练的那个人"设计的**：框架、约定、护栏、权限收窄（"免得实习生把生产库删了"）。

而这些东西，**正好是 agent 需要的东西**。

所以结论很实用：**护栏是可以后加的，但没有就得先补。** 她并不要求你先重写代码，她要求你先把"错误的选择"从 agent 的视野里拿掉。

### 7.2 新项目才是最大风险

反直觉，但逻辑很顺：全新项目**一条护栏都没有**。

你给 agent 一个任务，它会用**最方便的方式**解决。一次次累积下来，代码库开始**螺旋失控**——你不理解它，agent "大概理解"，而它一路优化的都是**短期便利**。她的原话是：最后"你会在那个应用上吃很多苦"。

这里有一个隐含的复利结构，值得点明：**没有护栏时，agent 的每一次"方便"都在给下一次增加成本。** 这跟你库里 10-05 那条讲的"规模上来之后缺的结构会以复利收账"是同一个机制，只是收账对象换成了代码库。区别在于，代码库的复利是**负向**的，而且不声不响。

### 7.3 约束有四层，别只靠最软的那层

这张表我认为是整场最可直接搬走的东西：

| 层级 | 手段 | 强度 | 逻辑 |
|---|---|---|---|
| 1 | **架构 / 框架** | 最强 | 让"正确写法"成为**最短路径**；agent 天生爱抄现成的，抄到的一定是对的 |
| 2 | **类型系统 / 编译器 / CI** | 强（能让 CI 变红） | "如果代码能编译，那它大概是好的"——她举 Rust 的 borrow checker |
| 3 | **lint / 静态分析** | 中 | 拦得住已知坏模式，拦不住没想到的 |
| 4 | **rules / skills / review bot** | 弱 | agent 会忘、会不一致；"只靠 rules 和 style guide，你的代码库迟早一团糟" |

她的第一原则一句话：**"the shortest path is the best path."**

这句话要反着读才有力：**不是因为最短路径好，是因为 agent 一定会走最短路径。** 所以你要做的不是"提醒它别走捷径"，而是**把正确解法修成那条捷径**。

落到她们的具体做法，细节都很小，但每一个都在消灭一类"需要人提醒"的情况：

- 框架 **Dune**，可以理解成"给 Electron 用的 Next.js"，**设计目标就是让 agent 写**；
- **禁 `useEffect`**——React 里最容易埋坑的钩子，CI 直接报错；
- **禁写注释**——因为 agent 会把一时的批评当成永久规则写进注释；
- **目录强制分层**：`electron/main` 与 `electron/renderer` 分开，CI 查 import 图，禁止跨层。原因是渲染线程一帧只有 16ms，重活漏进去就掉帧；
- **功能代码同居一目录**：状态、组件、逻辑都在 feature 目录下，agent 80% 的活在**一个目录**里干完。

## 八、一条判据：把 review 变成约束

如果整场只记一句话，我选这句：

> "Every time you have to do that, you should consider that as a code anti-pattern."

上下文是这样的：她说**最糟糕的位置**，是所有约束都靠人肉在 code review 里执行——你一条条读，然后说"这里不该这么写"。

她的建议是把每一次这样的 review 当成一个信号，然后问三句：

1. 能不能变成 **lint 规则**？
2. 能不能变成 **CI 失败**？
3. 能不能让**这个问题根本不存在**（架构层面消掉）？

这三句的强度是递增的，而大多数人只做到第一句就停了。**第二句开始才真正把人从环里拿出来。**

这条判据的好处是它可立即执行、不需要任何工具链改造：你下次说"这里不对"的时候，多花三十秒判断它属于哪一层。

## 九、成本：她的坦白

问答环节有人直接问：这套东西对**没有无限 token** 的团队成立吗？

她没有绕：

- 承认前提：**"我在一个 token 无限的实验室工作，我不能说所有人都该照我这个方式做。"**
- 但认为**可以**走到类似位置，关键是把问题换成 **ROI**：前期在 token 上花一大笔（重构、验证、约束），换取后面**保持很小很精简的团队**。
- 取舍说得很具体：**"是招一个人来做这件事，还是花 token 把代码库修到连最笨的 agent 都能干好？"** 她选后者——因为她工资贵，而这个框架"放在 pre-agent 时代，靠我一个人要写几年"。
- 一句定性：**"agent 的意义是让你做到你原本做不到的事，不是把 token 撒在每一件小事上。"**

关于数字，需要保持清醒。她口述上个月约 1000 个 PR、本月没过完已接近 800；媒体转述成"月均两千"。**那份 PR 列表没有任何人审计过，她自己说的数字比转述低。** 她主动提了这个争议，还自嘲"听起来像 slop artist"。

> 所以：**把机制当结论，别把数字当结论。** 数字是这套机制在特定条件下的输出，机制才是可以搬走的东西。拿数字当目标，你大概率会得到她自嘲的那种结果。

## 十、溢出：非工程师也能接活

最后一段问答容易被跳过，但它的含义比听起来大。

有人问：agent 这么能写，公司里其他职能怎么变？

她的回答围绕一个观察：Cursor 之前的产品（agent 窗口、CLI、IDE）本质都是**开发者工具**，PM 和设计师能在里面干活，但"体验说不上愉快"。而 Grok Bot（把每个 agent 当成有身份、可编排的个体）是"**对非技术人员的 Cursor 时刻**"——界面熟悉、门槛低。

结果是她团队里的 PM 和设计师**直接 ship 功能**：改完说一句"我修了个 bug，你看一下"，她 review 完直接盖章。

**这件事成立的原因不是"AI 变强了"，而是第七节那张表：Dune 的约束足够硬，所以不懂代码的人也不会把代码库搞坏。** 约束在这里的作用不是限制人，是**把能力下放给更多人**。

这条对一个单人项目同样成立，只是对象反过来：**约束足够硬，你才敢让 agent 在没有你的时段里干活。**

## 十一、这套方法在什么情况下会失效（我的判断，不是她的话）

她的方法有一个她没展开、但很关键的前提：**应用能被一条命令拉起来，并且能返回结构化结果。**

这对单人项目几乎总是成立的（Electron 桌面应用、单体服务、前端），所以她给的路子对你直接可用。但一旦系统变成"订单服务 + 支付服务 + 队列 + 几个数据库"，这个前提就没了，你会立刻掉进三种"伪闭环"：

| 伪闭环 | 看起来像 | 实际失效方式 |
|---|---|---|
| 打桩 / mock | 便宜、能并行 | mock 编码的是"上次有人看时依赖的样子"，真服务一改就漂移，而**失败是静默的**，合并后才炸 |
| 每次起整套环境 | 真实、隔离 | 成本 = 服务数 × 并发数，压不住 |
| 共用 staging | 真实、便宜 | 所有 agent 互相踩，一个坏改动变成所有人的红灯 |

**判据**：你的"闭环"如果依赖一份会过期的替身，那它不是闭环，是**延迟付款**。

对单个服务的项目，这条可以放心跳过；但如果你以后把 Jira 小助手拆成后端服务 + 飞书同步 worker，这条会立刻变成真问题。

## 十二、可搬走的五条

1. **先问"它能不能自己知道对错"，再问"它写得好不好"。** 前者决定你能不能并行，后者只决定你要不要返工。
2. **把每一次"我盯着它才没出事"当成缺陷记录。** 那说明验证还长在你身上。
3. **约束的强度顺序是：架构 > 编译器/CI > lint > 提示词。** 越往后越软，也越容易被人当成"已经做了"。
4. **每一次 code review 的纠正都是一条待落地的规则。** 落不下去，它就永远需要你亲口再说一遍。
5. **不要跳级开并行。** 本地看不清的事，上云只会放大几十倍，包括浪费。

## 落地清单（按"先做什么最划算"排序）

1. **给现有项目写第一个验证 skill**（今天，1 小时）：一条命令启动 + 截图/读关键 DOM + 打印核心结果。判据是"agent 跑完能自己说对没对"。
2. **给核心算法（比如混合检索）写一组固定 eval**（今天，30 分钟）：10 条 query + 期望 top-1，改权重前后跑一遍。没有它就谈不上"改进了"。
3. **写一张 feature map**（本周，1 小时）：入口、子功能、DOM 选择器、快捷键。以后截图说不清时，agent 自己能找。
4. **翻最近 10 次你说"这里不对"的原话**，逐条判断能否变成 lint / CI / 架构消解（本周，10 分钟）。
5. **把反复口述的 UI 约束落到代码里**（比如单行布局），别再靠对话提醒（本周）。
6. **等 eval 建起来之后，再考虑重构架构**（下个月）——没有 eval 的重构，你无法证明改对了。
7. **别追数字。** 一个月多少 PR 是结果，不是原因；原因是你有没有那层让 agent 自证的设施。
