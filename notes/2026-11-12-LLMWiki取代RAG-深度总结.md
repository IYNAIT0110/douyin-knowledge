## 一、这条视频真正回答的问题

"RAG 已经没人用、彻底过时"——最近网上这个论调越传越火。视频要回答的问题是：**LLM Wiki 到底是什么，它凭什么取代用了三年的知识库标配？**

先把话说明白：标题里的"彻底过时"是流量话术（第六节详述），但标题底下的技术判断是真的——**Karpathy 2026 年 4 月确实提出了一套新范式**，社区在两个月内长出了一排开源实现，"该不该换"已经是一个摆在桌面上的真问题，而不是博主造出来的。

## 二、RAG 的短板不是 bug，是结构

RAG（Retrieval-Augmented Generation，检索增强生成）的工作方式：上传一堆文档 → 用户提问时检索相关片段 → 拼进上下文交给大模型 → 输出答案。

视频指出的短板：

1. **每次提问才临时捞取碎片**——知识没法真正沉淀。这次问答学到的东西，下次提问不会变容易，检索成本和效果完全一样。
2. **模型只是被动调取切片**——它不会主动消化、串联新旧资料。第二份文档进来时，第一份文档在系统里还是一堆切好的碎片，两者互不打扰。

注意这两条都是**结构性**的：不是 RAG 实现得不好，是"提问时检索"这个时机选择本身决定了知识只被使用、不被积累。

## 三、LLM Wiki 换掉的东西：一个变量推出四个差异

LLM Wiki 的核心转向一句话能说清：**让大模型充当知识库的编辑与管理员，在文档入库的那一刻就深度精读、归纳、梳理，持续搭建一份可以互相跳转、关联引用的在线维基。**

视频给的四维对比，看着是四条，其实全部由**一个变量**推出——知识加工发生在提问时还是入库时：

| 维度 | 传统 RAG | LLM Wiki | 由"时机"怎么推出来 |
|---|---|---|---|
| 知识处理时机 | 提问时临时组装检索片段，用完即抛 | 计算前置到录入阶段，提前编译、长久沉淀 | 这就是变量本身 |
| 信息组织形式 | 切分后的文本块、向量碎片 | 结构化双向链接的维基页面 + 知识关联图谱 | 提问时来不及组织，只能切片；入库时有的是时间建结构 |
| 新增资料处理 | 只切块入库，新旧内容互不打扰 | 主动比对已有知识：新建概念页、更新旧内容、标注冲突 | 提问时的检索不知道"旧知识"长什么样；入库时的编辑手里就有整本维基 |
| 可读性 | 向量和切片人很难直接看懂 | 规整的笔记式页面，人可直接阅读、查阅、溯源 | 面向检索器优化 vs 面向人优化，产物形态自然不同 |

**这四行不用背。** 记住"计算时机"这一个变量，每一行都能现场推出来——这也是这条视频方法论上最值钱的地方：一个结构性变量 + 它的下游后果，比四条并列的 feature 清单有用得多。

## 四、三层架构与两阶段入库

### 4.1 三层架构

| 层 | 存什么 | 谁维护 | 关键约束 |
|---|---|---|---|
| 原始素材层 | 原始 PDF、网页、会议纪要 | 无人（入库后只读） | **不可篡改的事实源**，所有内容可回溯 |
| 维基呈现层 | 摘要页、实体页、主题页 | 大模型全权维护 | 增删页面、更新内容、维护双向超链接 |
| 规则约定层 | 预设的提示词规范 | 人设定 | 知识库该遵循什么结构、怎么归类新概念、如何处理互相矛盾的信息 |

分层的关键在**真理源的分离**：原始层永远不动，维基层随便改——错了可以删掉重建，因为事实还在底下躺着。这一点 Karpathy 原文里说得比视频重（他把 markdown 原始文件直接称为 source of truth，理由是躲开向量嵌入的"黑箱"问题：每条声明都能指回一个具体文件）。

### 4.2 入库两阶段

丢进一份新资料后走两大流程：

**分析阶段**：大模型通读全文、提炼核心论点 → 检索现有知识库 → 区分哪些是**全新信息**、哪些和过往记录**存在冲突**。

**生成阶段**：像维基编辑一样撰写、修订页面——给新实体建词条、补充原有词条细节、给相关页面加上关联。**遇到关键冲突不会粗暴覆盖，而是清晰标注不同来源的分歧。**

"冲突标注"是整个流程里最容易被一笔带过、其实最见功力的一条：它承认了知识库不是真理的集合，而是**带出处的分歧的集合**。一个只覆盖不标注的系统，会在第二份资料进来时悄悄丢掉第一份资料里的反例。

### 4.3 两类适用场景

1. **企业内部知识库**：团队知识散落在聊天记录、需求文档、会议录音里，没人愿意手动整理。接入后日常沟通自动沉淀成体系化百科，新人上手直接拿到一份持续更新、逻辑连贯的内部手册。
2. **竞品调研等复杂情报**：不同渠道的数据经常打架，传统 RAG 随机捞出一段、很容易以偏概全。LLM Wiki 在入库阶段就识别出矛盾，在词条里写清楚：来源 A 给出的数据是多少，最新来源 B 的结论又是什么——帮我们避开信息陷阱。

两个场景的共同点：**价值不在"答得快"，在"信息互相矛盾时答案仍然可信"。**

## 五、外部核实：Karpathy 的原始主张长什么样

视频说"2026 年 Karpathy 提出 LLM Wiki"。核实结果：

| 核验项 | 结果 |
|---|---|
| 提出时间与形态 | ✅ 2026-04-03 发于 X，两天后补发 GitHub Gist——他称之为 **"idea file"**：故意写得抽象，让人丢给自己的 agent 按自己的工具链实现 |
| 原始名称 | 原文叫 **LLM Knowledge Bases**，"LLM Wiki" 是社区通称 |
| 原始工作流 | raw/ 目录（Obsidian Web Clipper 存网页为 markdown）→ **compile pass**（LLM 读原始层、生成概念页、建反向链接）→ query loop（提问时让 LLM 自己翻 wiki）→ **lint pass**（健康检查：扫不一致、补缺失、找新关联） |
| Karpathy 自己的规模 | 约 **100 篇文章 / 40 万词**，前端用 Obsidian，LLM agent 与 Obsidian 并排开着实时看编辑结果 |
| 开源实现 | ✅ 至少四个活跃项目：nvk/llm-wiki（Claude Code 插件）、nashsu/llm_wiki（GUI 桌面应用）、Pratiyush/llm-wiki（对话历史转静态 wiki）、lucasastorian/llmwiki（MCP 驱动自动维护） |
| 视频的"三层架构" | ⚠️ 方向与原文一致，但**三层是社区文章的总结框架**，不是 Karpathy 原话——博主转述时没区分，本文替他标出 |

一句话：视频没有编造，但把"社区已经消化两轮的二手框架"当成了"Karpathy 的原始设计"来讲。对学知识无伤大雅，对溯源有影响。

## 六、视频没说的三个坑（外部信源补齐）

这是本文最该写的一节。视频把 LLM Wiki 讲成了单方面碾压，外部主流信源的结论却是 **"complement, not replace"（互补，不是替代）**：

**1. 幻觉烘焙（hallucination baking）**
RAG 每次提问都回到原始文档，模型答错一次，下次还有机会对，因为事实源还在。LLM Wiki 改变了这一点：模型在编译时把猜测和脑补**写成了页面**，之后每一次提问都信任这个页面。零散的错误容易发现，**有组织、持久化的错误最难发现**——它读起来通顺、有结构、有链接，看起来完全像真的。所以 lint pass 的重点不是查断链和孤儿页，是查"看着很像真的"的论断。

**2. 入库不免费（ingest is not free）**
查询时显得轻，是因为重活提前干完了，但活没消失、只是搬家了。每份新文档要经多轮 LLM 调用（读、总结、链接、合并）。数据频繁变化的场景（流式信息、快变语料），反复重编译的成本会反超 RAG——RAG 永远直接从最新源里取。

**3. 规模天花板（scale ceiling）**
"bye-bye RAG" 的叙事默认 100 页能行的东西到 10000 页也能行——不能。wiki 长到超出上下文窗口后，底下还得垫一层真正的检索 substrate，而最便宜的 substrate 恰恰是向量嵌入。**绕一圈，RAG 又回来了**——只是从"全部知识的检索层"退到"wiki 底下的托底层"。

加上视频自己略过的：RAG 在**百万级文档、多租户、硬延迟约束**（如客服机器人）场景仍然占优。诚实的架构是混合：wiki 做编译与关联层，向量检索做规模托底。

## 七、落到你身上：Jira小助手正好站在甜蜜区

这条是本库最贴你项目的一条素材。Jira小助手现在是：飞书 Bitable 双通道同步 → kb.json（约 763 条 bug 记录）→ TF-IDF + embedding-3 混合检索（0.65 语义 / 0.35 关键词）。

拿视频的判据过一遍你的系统：

| 视频的判据 | Jira小助手现状 |
|---|---|
| 提问时临时捞碎片、用完即抛 | ✅ 现状就是：每次查询现算 TF-IDF + embedding，查询之间不沉淀 |
| 新旧内容互不打扰 | ✅ 763 条记录彼此独立，同类 bug 的共性没有结构化载体 |
| 知识散落、要人脑串联 | 部分：排查同类报错时，根因和复现条件散在多条记录里 |

而三条"不适用"的坑，你一条都不踩：763 条远没到规模天花板；bug 库更新频率可控（不是流式数据）；单人使用不存在多租户延迟约束。**这正是 wiki pattern 的甜蜜区。**

可试的增量动作（不动现有检索链路）：给**高频重复出现的 bug 主题**编译词条页——现象 / 根因 / 解法 / 关联哪些记录编号。检索时先查词条、再查原始记录；词条本身也回答"这类问题以前出现过几次"。三层对应到你的系统就是：kb.json（事实源，只读）→ 词条页（模型维护）→ 归类规则（提示词约定）。

但保留一句（我的判断，不是视频的）：你的检索痛点如果是"查不准"而不是"查到后要串联"，词条层收益有限——**先做第五节那三个坑的自检，再决定动不动手**。

## 九、一句话结论

LLM Wiki 没有杀死 RAG，它把"知识是耗材还是资产"这个选择第一次摆到了明面上：**提问时加工，知识就是一次性耗材；入库时加工，知识才开始复利**——代价是你要付编译的钱、扛烘焙错的风险、认清规模的墙。763 条 bug 记录该不该开始复利，是这条视频留给你的问题，答案只在你的重复 bug 出现频率里。
